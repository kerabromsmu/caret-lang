  ## Findings

  1. High — Reserved spellings are accepted as declarations and parameters, creating unreachable bindings

  src/main/java/caretlang/Parser.java:61 accepts any IDENT on the left side of a definition, while expression parsing interprets identifiers such as true, false, not, and, and or specially.

  For example:

  true = 7
  print true

  prints true, not 7. Similarly:

  f true = true
  print f 7

  prints true; the parameter is impossible to reference.

  The same problem affects _, which is interpreted as a hole in expressions. This silently accepts nonsensical source rather than diagnosing it.

  Recommendation: define identifier/keyword policy centrally and validate every binding name and parameter during parsing or semantic analysis. Add negative tests for constants, operators, _, and future reserved words.

  2. High — Valid recursive programs can terminate the interpreter with an unhandled StackOverflowError

  Function calls recursively invoke Java through src/main/java/caretlang/Interpreter.java:82 and src/main/java/caretlang/Value.java:169. A sufficiently deep valid Caret recursion leaks a Java stack trace:

  f n = n == 0 & 0 ! f (n - 1)
  print f 100000

  This bypasses located Caret diagnostics and can abruptly kill the REPL or test runner.

  Recommendation: eventually use an explicit evaluation stack or trampoline. Until then, impose a documented call-depth limit and report a located CALL_DEPTH_EXCEEDED diagnostic. Avoid catching StackOverflowError as the primary
  long-term design.

  3. Medium — File-system errors leak raw Java stack traces

  src/main/java/caretlang/Main.java:36 and runTests call Files.readString outside their language-error handling. Running a missing file produces an uncaught NoSuchFileException stack trace.

  This contradicts the CLI’s otherwise clean diagnostic boundary and makes normal operational failures look like interpreter bugs.

  Recommendation: handle expected IOException failures at the CLI boundary, include the path and operation, and return nonzero without a stack trace. Cover missing, directory-as-file, invalid encoding, and unreadable-file cases.

  4. Medium — Extra CLI arguments are silently ignored

  Outside test mode, src/main/java/caretlang/Main.java:34 reads only args[0]. Thus:

  caret program.caret accidental-extra-argument

  runs successfully and ignores the mistake.

  Recommendation: require exactly one argument in file mode and print usage for unsupported argument counts. Centralizing command parsing would also make future subcommands safer.

  5. Medium — Runtime kind logic is duplicated and already inconsistent

  Value-kind classification appears separately in:

  - src/main/java/caretlang/Interpreter.java:273
  - src/main/java/caretlang/Interpreter.java:427

  They disagree for null:

  print type ?
  print (@?).kind

  produces:

  Nullable
  Null

  Nullable sounds like a contract category, while reflection reports the concrete runtime kind. Whether this distinction is intentional is not specified, but two manually synchronized switches guarantee further drift as values
  are added.

  Recommendation: settle the observable terminology in LANGUAGE.md, then give each value kind one language-owned descriptor used by type, reflection, diagnostics, and future contracts.

  6. Medium — Partial-application handling duplicates AST traversal and can become quadratic

  Hole processing contains separate recursive implementations for:

  - collecting holes,
  - counting holes,
  - eager capture,
  - binding holes.

  See src/main/java/caretlang/Interpreter.java:460.

  captureNonHoleParts calls containsHole at every recursive node, and containsHole walks the entire subtree again. A large skewed expression containing holes therefore approaches quadratic traversal time. Applying the partial
  then reconstructs the expression tree before evaluating it.

  This is also a maintenance trap: every new Ast.Expr subtype must be added consistently to several switches.

  Recommendation: perform one analysis/lowering pass that returns hole shape and a captured executable representation together. A common AST visitor/folder would remove repeated structural switches. Evaluate bound holes directly
  rather than rebuilding a complete AST for every final invocation.

  7. Medium — Persistent collection construction is quadratic

  src/main/java/caretlang/Value.java:80 copies the complete sequence for every append. src/main/java/caretlang/Value.java:114 does likewise for dictionaries.

  Repeatedly building a collection of n elements is therefore O(n²) in time and allocations. This matters because the roadmap intends to build a Caret-written lexer/interpreter using these primitives.

  Recommendation: introduce genuinely persistent collection storage, or at minimum an internal builder/transient representation that freezes to an immutable value at an observable boundary. Add scaling tests before the self-
  hosting phase.

  8. Medium — Interpreter is accumulating too many unrelated responsibilities

  src/main/java/caretlang/Interpreter.java:8 currently owns:

  - declaration validation and predeclaration,
  - lexical-environment setup,
  - AST evaluation,
  - arithmetic and equality semantics,
  - partial lowering and capture,
  - all built-in registration,
  - collection validation,
  - reflection,
  - test-runner built-ins.

  This already conflicts with the project rule to separate semantic analysis, evaluation, runtime values, and diagnostics. It will complicate contracts, effects, operators, and compilation because those features will otherwise
  be added to the same central switch.

  Recommendation: prioritize the planned resolver/semantic-analysis pass. Separately extract built-in registration, value operations/equality, reflection descriptors, and partial lowering.

  9. Low — REPL behavior is implemented twice

  There is a JLine loop in src/main/java/caretlang/JLineRepl.java:33 and a second Scanner-based loop in src/main/java/caretlang/Main.java:46. The latter is effectively a test-only pathway because main() selects JLine directly
  when no arguments are supplied.

  The implementations already differ in banner text, terminal behavior, history, and exception handling.

  Recommendation: make the input mechanism injectable behind one REPL loop. Tests can use a noninteractive reader without maintaining a second user-visible implementation.

  10. Low — Layout preprocessing duplicates partial lexical logic

  src/main/java/caretlang/Parser.java:123 scans strings, escapes, comments, and delimiters independently of src/main/java/caretlang/Lexer.java:14.

  That duplication is currently small, but upcoming multiline constructs will require both scanners to agree on every string/comment/delimiter rule. The implementation tracks only aggregate delimiter depth, not delimiter kinds.

  Recommendation: introduce the layout/tokenization layer already anticipated by the roadmap, with one lexical state machine shared by logical-line construction and token emission.

  ## Testing gaps

  The existing tests cover ordinary success cases and diagnostics well, but the highest-value missing categories are:

  - reserved or context-sensitive binding names;
  - missing/unreadable files and malformed CLI invocation;
  - recursion-depth/resource exhaustion;
  - large partial expressions and repeated collection construction;
  - consistency between type, reflection, rendering, and equality for every Value subtype;
  - adversarial delimiter/layout combinations;
  - Unicode identifiers, if they are intended to be supported.
